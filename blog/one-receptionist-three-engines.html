One receptionist, three engines

Aug 26, 2026 / 9 min read / 962 words / Christian John
VoiceMake.comn8n
On this page

    Most "Make vs n8n vs Zapier" content is spec sheets copied from pricing pages. So I did something dumber and more useful: I built the same AI phone receptionist three times — once per platform — over one shared voice layer, and wrote down everything that broke.

    The project: when a clinic misses a call (or it's after hours), an AI voice agent answers, handles questions about services and hours, captures the caller's name, number and preferred slot as structured data, books the appointment on Google Calendar, logs everything and alerts the front desk. The repo is public: voice-receptionist. A 🔒 HIPAA-compliant build is available for healthcare practices — BAAs, access controls and audit logging on request. The public demo is not for PHI.

    The shared spine

    All three branches consume the same contract: a Retell call_analyzed webhook carrying a transcript plus structured data (caller_name, callback_number, intent, service, preferred_slot). Every branch then does the identical dance — validate, conflict-check Google Calendar, book, log, alert the front desk through a configurable channel.

    Because the voice layer is shared, comparing platforms is apples-to-apples. And because only one branch needs to be live at a time, switching engines mid-pitch is literally changing one webhook URL in Retell's dashboard.

    Make.com: fast to build, sneaky to debug

    Make got me working fastest. Native modules for Retell reports, Google Calendar and Telegram meant almost no custom mapping, and the scenario history shows every module's inputs and outputs — genuinely great debugging UX.

    Then the IML expression language fought back. There is no and(), no or(), no empty(). A simple "bookable AND future slot" becomes nested-if() spaghetti. My favorite trap: a filter condition referencing a bare word like book_appointment treats it as an identifier, silently evaluating to null — so my fallback route matched every call, including bookings, and overwrote their log status seconds after booking. The run still reported success.

    Two more personality traits: any error auto-deactivates the whole scenario (surprise downtime), and Make routers execute every matching route, not just the first. Both are documented behaviors that will absolutely ruin your afternoon if you assume otherwise.

    n8n: the developer's engine

    Self-hosted n8n is where the logic got clean. A Code node replaced twenty expressions with fifteen readable lines of JavaScript. Built-in Data Tables gave me a free database. The Switch node actually understands routing.

    The tax: you own the plumbing. Webhook payloads arrive wrapped under body, the Set node wants its assignments double-nested in a way no tutorial mentions, and the Google Calendar node refuses Service Accounts — OAuth2 credential or nothing. That last one cost me a rebuild of my auth plan, but the fix was one browser click, and afterwards the workflow felt indestructible. No op quota. No auto-shutdown. Version-controllable JSON.

    Field test #1: the call that never reached the workflow

    With the n8n build live and a Retell agent answering, I finally pointed a real browser call at it — no phone number, just WebRTC and a microphone. Two calls, both instructive, neither one a success.

    The first connected and lasted eleven seconds. The transcript contains exactly one line: the agent's greeting. No caller audio. The second never joined at all — Retell recorded it as error_user_not_joined with a duration of zero.

    Meanwhile n8n reported two manual test runs as successful. Both contained no node output whatsoever. That's the trap: this workflow starts from a polling trigger that asks Retell once a minute for calls that have ended. Run it by hand and the trigger finds nothing, the graph stops, and n8n still calls the run a success. "Success" meant "nothing errored", not "something happened".

    The other finding was in the trigger config: it only fetches calls with status ended. My failed call was error, so even with everything working it would have been filtered out. The calls a clinic most needs to know about — the ones that die before anyone speaks — are exactly the ones that vanish.

    So the pipeline was never wrong; it was never reached. Empty execution logs are not a bug report about your booking logic, they're a bug report about your input. Fix the microphone, confirm a call has a two-sided transcript, then watch for a run with mode trigger instead of manual. That's the only evidence that counts.

    Zapier: the client's engine

    Zapier is the one I can't build programmatically — Zaps are click-ops only — yet it's the one clients love most. The killer pattern: keep configuration in a Google Sheet "Config" tab (alert email, business hours) and look it up at runtime. Non-technical staff edit a spreadsheet; the Zap never changes.

    The costs are real though: Webhooks by Zapier sits behind plan tiers, tasks burn on every webhook call, Telegram isn't native (Gmail alerts instead), and Paths are clunky next to even Make's router.

    Pick by maintainer, not by feature list

    That's the whole lesson. The receptionist logic is identical everywhere; what differs is who suffers when it changes. Client-managed? Zapier, because they can read it. Agency-managed? Make, because you'll debug it fast. Self-hosted or privacy-sensitive client? n8n, because they'll own it forever.

    Full scorecard, war stories and the plug-in checklist live in the repo. The n8n pipeline now takes real calls — the first field test above is what that looks like before the microphone cooperates. If your clinic phone rings off the hook and answers itself badly, we should talk. 🥔
