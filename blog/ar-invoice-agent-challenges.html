The invoice chaser: three bugs, one rule

Oct 28, 2026 / 7 min read / 1,199 words / Christian John
n8nLLMOps
On this page

    Chasing overdue invoices is the work nobody schedules. It's not hard, it's just always later — until a receivable is 90 days old and the polite reminder you meant to send in week two would now read like an apology for your own silence.

    So I built ar-invoice-reminder-agent: an n8n workflow that reads an invoice tracker every morning, works out how late each invoice is, and drafts a reminder whose tone matches the delay. Friendly under two weeks, firm to thirty days, solution-oriented after that. Every draft lands in Gmail. None of them send themselves.

    The build was mostly unremarkable. The failures were not. Three of them changed the design, and one rule decided all three.

    The shape of it

    Ten nodes, one straight line:

    1. A schedule trigger fires at 09:00.
    2. Google Sheets returns every row of the Invoices tab.
    3. A Code node drops paid and void rows, parses amounts and dates, computes Days Past Due, assigns a tone, and formats the currency.
    4. A Gemini 3 Flash agent writes the email from that normalized row.
    5. A Structured Output Parser forces { "email_subject": "...", "email_body": "..." }.
    6. A second Code node cleans the result, enforces the signature and falls back to a template if the model produced nothing usable.
    7. Gmail files a draft addressed to the client — no send.
    8. Google Sheets stamps the follow-up date back onto the matched row.
    9. The AI model and parser hang off the agent as sub-nodes.
    10. A sticky note explains the whole thing on the canvas.

    The model gets one job: turn a row into prose. Every decision that can be made deterministically — how late it is, which tone applies, whether this invoice was already chased — is made in code before the model is ever called.

    Bug one: the model answered with nothing

    First end-to-end run. Sheets read, code ran, and then:

    The AI model returned an empty response
to the Structured Output Parser

    The agent node reported an error after five seconds, the parser errored in three milliseconds, and the run stopped. Nothing in the prompt was broken. Nothing in the row was broken. The model simply returned an empty string to the parser.

    The cause was a number I'd set by reflex: maxOutputTokens: 700. On a reasoning model that budget is shared between thinking and answering. Gemini 3 spends tokens working out the email before it writes it, and 700 was not enough to reach the JSON. The parser asked for structure, the model had already run out of room, and the empty result read like a schema problem.

    Raising it to 4096 fixed it instantly. Same prompt, same rows, valid JSON every time. The lesson isn't "use bigger numbers" — it's that a token limit is a correctness setting when you use a reasoning model. The failure surfaces at the parser, which is the last place you'd look.

    Bug two: the model kept rewriting the sign-off

    The prompt asks for exactly this, every time:

    Regards,
[Billing Team]

    Most of the time it complied. Some of the time it produced a signature with a company name attached, an extra blank line, or a sentence thanking the client for their patience after the sign-off. None of that is wrong writing. All of it is wrong output — a template that's identical across hundreds of invoices is exactly the thing you don't want a language model freelancing on.

    So the workflow stopped trusting it. The validation node finds the last Regards,, deletes everything from there to the end, and appends the two lines itself. It also unescapes any literal \n the model left in the body and strips markdown fences and bold markers.

    This is the pattern I keep coming back to: let the model write the paragraph, never the contract. The signature, the JSON keys, the placeholders-to-avoid list — those get enforced in code, because code doesn't have a bad day.

    Bug three: the same invoice, chased every morning

    The first version had no memory. The schedule fires daily, the sheet has the same overdue rows, so the next morning it drafted the same three reminders again. And again. The drafts folder fills, the notes column fills with duplicates, and eventually someone trusts the automation less than their own memory.

    The fix is a seven-day gate in the normalize step: if Last Follow-Up Date is within the last week, skip the row. It runs before the model call, which also means a skipped invoice costs nothing.

    Two details made this less trivial than it sounds. Sheets hands back dates in more than one shape — formatted strings, real dates, and occasionally raw serial numbers — so the parser handles all three before comparing. And the cooldown is deliberately not something the model decides: a language model asked "should I chase this again?" will always find a reason to say yes, because the row in front of it looks overdue. That's not judgment. That's just the data.

    The small bug that was actually a measurement bug

    My validation node counts sentences, because the brief says the email body must stay under four. The first verified run reported Sentence Count: 5 on an email that was plainly three sentences.

    The counter was matching every . — which meant $1,500.00 ended a sentence twice, and so did the payment link. The prose was fine; the ruler was broken. Strip URLs and currency amounts first, and the count lands on three.

    It's a tiny bug with a useful lesson attached: when a guardrail fires, confirm the guardrail before rewriting the thing it guards. I nearly "fixed" a prompt that was already doing its job.

    One more thing the test run taught me

    I verified the workflow against the real tracker, which is exactly what a careful person would do — and it created three real Gmail drafts and wrote three real follow-up dates into the sheet. Nothing was sent, so nothing was damaged. But the tracker now honestly says those invoices were chased today, and they'll sit inside the cooldown for a week.

    The next build gets a copy of the sheet for testing. Draft-only means the blast radius is small, not zero: writes are still writes.

    The one rule

    All three bugs point the same direction. The model is good at the part that needs judgment — phrasing an awkward request so a client still takes your call — and bad at the parts that need to be identical every single time: schema, signature, arithmetic, whether this row has already been handled.

    Automation should delete drudgery, not judgment. Computing days overdue is drudgery. Deciding whether an invoice is worth a payment plan conversation is judgment. Drafting the email is the interesting middle — close enough to judgment that a human should still see it before it leaves the building, and repetitive enough that nobody should be typing it at 11pm.

    So the workflow chases, and a human sends. That split is the whole product. 🥔
